## 3. Engine label is now VIN-authoritative

**Trigger:** a 2025 Toyota Tacoma scan showed an engine description that didn't align
with the VIN.

**Ground truth — NHTSA decode of `3TMKB5FN3SM028992` (clean, check digit OK):**

| Field | Value |
|-------|-------|
| Make / Model / Year | TOYOTA / Tacoma / 2025 |
| Engine | **2.4L, 4-cyl, EngineModel `T24A-FTS`, 278 HP** |
| Drive type | 4x2 |
| Body | Pickup |

**Key finding:** the **badge** (`2.4L 4-cyl T24A-FTS`) already matched the VIN — it's
built from the NHTSA decode (`identify/route.ts` ~line 434). The real problem was the
**Engine part's description**, and the cause is architectural:

- The web client sends every photo to `/api/identify` **in parallel**, one call per
  photo (`AddVehicle.tsx` `runAnalysis`).
- The server's VIN enrichment only fired when the VIN **and** the engine were in the
  **same photo** — but the VIN is on the windshield and the engine is in the engine
  bay (**different photos**). So the engine part was **never reconciled to the VIN**;
  its description stayed as the vision model's per-photo guess.
- Worse, the old enrichment only **appended** the VIN line instead of replacing the
  guess, so it could self-contradict.

**Fixes implemented:**

1. **Client merge — `web/src/components/views/AddVehicle.tsx`** (the real fix): new
   helper **`applyVinSpecsToParts(parts, agg)`** runs at merge (the only point where
   the windshield VIN and the engine-bay part are together). When a VIN engine is
   known it relabels:
   - Engine → name `Engine — 2.4L 4-cyl T24A-FTS`, description
     `2025 TOYOTA Tacoma engine — VIN-confirmed 2.4L 4-cyl T24A-FTS.` (+ wear notes preserved)
   - Transmission → VIN drivetrain (`4x2`) noted.
   - No-op when there's no decoded engine (non-VIN scans untouched).
2. **Server — `web/src/app/api/identify/route.ts`**: VIN enrichment now **replaces**
   (not appends) the engine description, so the same-photo case and the mobile/
   extension callers can't produce a contradiction either.

**Status:** ✅ implemented, type-checks clean, reviewed and approved.

## 4. PENDING — VIN-aligned engine *pricing* (not yet implemented)

Goal: the engine **price** should reflect the VIN-confirmed engine, not the vision
model's per-photo guess. Designed, not built. Planned approach:

1. **New endpoint `web/src/app/api/part-price/route.ts`** — given
   `{ query, grade }` (e.g. `"2025 TOYOTA Tacoma 2.4L 4-cyl T24A-FTS engine"`, `"B"`):
   auth like `/api/identify`, ask Gemini 2.5 Flash for the brand-new OEM price, parse
   it (reuse `parseGroundedPrice`), then apply the **same** `usedPriceFromNew(newPrice,
   grade)` formula the scan uses — so the engine stays consistent with every other part.
   Returns `{ newPartPriceUsd, suggestedPriceUsd }`.
2. **Client wiring — `AddVehicle.tsx`**: after merge, when `agg.engine` exists,
   async-call `/api/part-price` for the engine part and update its
   `suggestedPriceUsd` / `_aiPrice`. Best-effort: keep the scan price on failure;
   grade C stays unpriced.

**Notes / gotchas found while designing it:**
- Re-pricing needs the part **grade (A/B/C)**. At runtime the client's
  `p.condition` IS `A/B/C` (confirmed via `ConditionBadge` in `UI.tsx`), even though
  the `AIPart.condition` TS type wrongly says `"Good" | "Poor"`.
- That same type bug makes the report's **"N graded Good" always show 0** (it filters
  `p.condition === "Good"`, but the value is `A/B/C`). Worth fixing separately.
- Endpoint can't be tested locally without `GEMINI_API_KEY` (see §1).
